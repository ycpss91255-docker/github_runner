github_runner 架構總覽

Ephemeral JIT self-hosted GitHub Actions runner 基礎建設

相關 ADR: ADR-0001, ADR-0002, ADR-0003, ADR-0004, ADR-0005

1. 系統拓撲

四個邊界層：GitHub Scale Set API、Go listener、Bash shell-out、Container engine。每層有明確的職責分界（ADR-0003）。

ADR-0003 邊界原則：Go 持有所有 policy 決策（何時准入、pool 大小、capacity 回報）；Bash 持有所有 I/O 操作（container run、/proc 讀取、orphan 掃描）。兩側透過 exec.CommandContext + 明確的 argv/env 契約溝通。

2. Go/Bash 邊界與模組依賴

Go side 與 Bash side 的模組關係。每個 Go interface 對應一個 Bash shell-out 實作（ADR-0003）。

3. 部署拓撲

一台 host 上的檔案配置與 systemd 管理。deploy-listener.sh 是唯一入口指令。

4. Job 資料流

一個 GitHub Actions job 從 assignment 到 container 執行到 history capture 的完整路徑。

5. 從零建置

一台什麼都沒有的機器, 到跑完第一個 job。Ephemeral 路徑不經過 init.sh -- deploy-listener.sh 是自足的。

6. 擴充路徑

已經有一個 runner type 在跑之後, 四種擴充方向 -- 各自的動作與代價不同。

最貴的錯誤是 labels 寫錯。 它不會報錯 -- job 只會靜靜卡在 queued, 而且 job 的 REST status 在被指派給 scale set 之後本來就還是 queued, 所以 queued 本身不構成證據。以 scaleset-admin 印出的那行 runs-on: 為準。

7. Deploy 流程

deploy-listener.sh 的執行路徑 -- 第 5 節 Phase 3 的展開。

8. Teardown 流程

teardown-listener.sh：deploy 的反向操作，只影響本機。

9. Status 查詢流程

status.sh 列出本機的 runner 並交叉比對 GitHub 狀態。

10. Cleanup 流程

cleanup.sh 清理 runner 殘留。可排程（schedule-cleanup.sh）。

11. Remove / Update / Set-labels 流程

互不相干的 runner 生命週期操作。

12. Provision 生命週期

Go listener 內部的 per-job 生命週期：從 worker pool acquire 到 container teardown。

13. 反應式准入

ADR-0005 的 CPU/RAM reactive live-admission。每個 job 准入前以 live host reading 判斷。

14. Runner-type Config Schema

deploy/runner-types.sample.yaml 的 schema 與每個欄位的流向。

Field Required Consumer Description
name yes Go loader, logs operator-facing id; unique across config
scale_set yes Go loader -> session GitHub scale set identifier; unique. NOT the routing key
labels yes scaleset-admin create THE routing key: what runs-on matches. Fixed at scale set creation
image yes ProvisionRequest container image; pin by digest for supply-chain safety
devices no ProvisionRequest -> env host device nodes for --device passthrough (no --privileged)
runtime no ProvisionRequest -> env container runtime shim (e.g. nvidia); empty = engine default
build_tool no ProvisionRequest -> env daemonless builder (kaniko/buildkit); empty = none
concurrency.mode no wiring.go "" = reactive (default); "auto" = GPU device sizing
concurrency.reserve no reactive admission percent headroom to keep free; 0 = default 10; upward-only, min 10
labels vs scale_set: scale_set 只是 identifier。Workflow 的 runs-on 匹配的是 labels。兩者只在 scale set 建立時 labels 設為 scale set name 的情況下才相同。搞錯的唯一症狀是 job 靜靜卡在 queued，沒有任何 error。
